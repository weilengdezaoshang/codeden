调研日期：2026-08-30 至 2026-08-31。配套 [PRD v0.5](eval-platform-closed-loop.md)。只使用论文、项目仓库与维护者官方文档；论文结论不等于某个 UI 的行业标准，也不代表本项目已经接入这些工具。

## 2. 修正原方案的六个具体问题

### 2.1 “AI 觉得通过”不是完成证明

原方案已有默认评分器，但缺少明确的必选验收条件。改为：程序能验证的结果交给程序验证；沟通、人格或语义要求交给受约束的 AI 评审。每条结果展示判据、事实和证据入口。失败的检查不能被其他维度的好表现平均掉。

这里是对上述资料的产品化选择，不是要求所有项目都采用同一种聚合算法。

### 2.2 “错误”不能全部算失败，也不能全部排除

容器启动失败、评分服务不可用与 Agent 输出错误不同。反过来，任务明确限定调用预算且 Agent 超限，也不能用「技术错误」把失败洗掉。按事先固定的验收条件及真实证据判断，未知时保持未判定；总数和未判定数量始终可见。

### 2.3 “完整 Trace”不是一段最终回答

来源记录保留任务边界与必要上下文；新执行链路记录每次实际调用、工具、结果和独立验证。并行工具、子 Agent 用父子关系表达，缺失步骤显示缺失。不固定为四步，也不展示无法取得的内部推理。

### 2.4 “去重”与“相似归类”必须分开

所查资料没有证明一种通用语义去重规则能适用于我们的私有代码任务。因此首版保守采用：上传幂等；同权限、同任务条件下完整证据相同才折叠；相似但不相同的记录只分类，不自动丢弃或共享审核结论。保留原始来源，不能用上传频次当线上故障率。

### 2.5 “人工同意入库”不等于用例能测出问题

入库检查应回答：输入是否自足、预期是否明确、环境是否独立、验证是否真的区分正确与错误。优先复用经过正反例验证的检查模板；新增程序验证必须证明不会空跑通过。参考答案不是唯一措辞，已知错误的线上回答更不能当参考答案。

### 2.6 “本次通过”不等于已经稳定解决

v0.9 将重复试验和同条件版本对比提升为 P0：默认每题 5 次，单次只保留为显式冒烟。5 次是本项目的成本折中，不是论文证明的充分样本量。全部计划试次保留，故障重试不增加样本数，不挑最好一次覆盖原结果；报告分子、分母、判定覆盖率和每题区间。τ-bench 的 pass^k 与至少一次成功的 pass@k 含义不同，首版不混用或展示这两个指标。具体口径见[重复评测实验规格](eval-repeat-experiments.md)。

## 3. 明确不引入的复杂度

- 不增加第三个导航入口，不引入评分器管理页、自动根因定位和发布观察流程。
- 不为每条上传 Trace 自动跑模型，不默认花上传者的 Token 做审核。
- 不因为参考 Python 评测框架就把现有 Node 平台改成 Python；先借鉴契约和数据流，需要支持特定官方 harness 时再适配。
- 不把 Langfuse 支持生产数据转 dataset 的能力理解为自动获准复制用户数据；本项目仍独立执行授权、用途和隐私检查，也不用于训练。
- 不把评测集用例通过率外推为线上总体质量；样本经过选择、去重和人工改写，分布已经不同。

## 4. 证据强弱与边界

SWE-bench、τ-bench 直接涉及 Agent 的任务/环境评测；MT-Bench 主要研究聊天模型评审偏差，只用于支持 judge 校准的必要性。Inspect 与 Langfuse 提供可核查的开源工程模式，但其界面不是必须复制的标准。

PRD 中的状态聚合优先级、审核按钮、去重指纹边界、隐私策略及 P0/P1 划分是本项目的设计决策，不伪装成论文结论。所有首版展示先服务于「选集启动、理解结果、审核入库」这三件事。
