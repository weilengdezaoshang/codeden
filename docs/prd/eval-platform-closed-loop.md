## 1. 两条独立、相互衔接的流程

离线评测：选择评测集和被测配置 → 设置每题次数 → 确认总试次与预算 → 每次从干净环境执行 → 独立判卷 → 汇总每题多次成绩 → 查看失败证据 → 修改 Agent 后创建同条件对比实验。一次 Job 表示一场实验，一个 Trial 表示一道题的一次计划内执行，不要求拆成多个项目。

Trace 审核：用户 Agent 上传到本平台后端 → 查看去重后的记录与分类 → 人工开始审核 → 整理独立用例 → 加入指定离线评测集。

「开始审核」只是本平台内的状态变更，不是再向其他系统上传一次。接收 Trace 时不自动调用评分模型，也不自动判断是哪一层导致问题。离线评测重新执行整理后的用例，不重放用户的真实项目。

## 2. 只有两个入口

| 页面                 | 用户要做什么                              | 展示什么                                                       |
| -------------------- | ----------------------------------------- | -------------------------------------------------------------- |
| 离线评测（默认首页） | 选择评测集并启动，查看总结果和逐条原因    | 进度、通过/不通过/未判定数量、结果筛选、按需展开的执行链路     |
| Trace 审核           | 查看上传记录，去重/分类后在同页审核并入库 | 原始事实、重复记录数、分类筛选、用例编辑、暂不采用、目标评测集 |

没有评分器配置页、插件市场、自动归因页、负责人认领和发布观察页。详细链路折叠在记录详情里，日常审核不需要理解底层字段。

界面默认回答三个问题：「跑得怎样」「为什么这样判」「下一步做什么」。使用数量、可筛选分段条和少量可点击的证据节点；不增加雷达图、综合质量大分或复杂可编辑流程图。判据可定位对应证据，原始字段按需展开。这个层级借鉴 [Inspect 的结果与日志下钻](https://inspect.aisi.org.uk/log-viewer.html)，具体布局是本项目的简化选择。

## 3. 上传记录

Agent 异步上传到同一平台的接收接口；失败由本地 Outbox 有界重试，不阻塞用户任务。上传接口进行身份与权限检查、大小限制、脱敏策略校验、幂等去重和持久化，成功保存后才返回已接收。同一上传 ID 的不同内容返回冲突。

列表默认看任务标题和状态。详情先看原始任务、Agent 实际回答和工具执行结果；点击「完整记录」才展开模型实际请求与响应、当时的工具列表、参数、结果和已采集的用量。

一条记录对应一次有明确边界的任务，不默认等同于一次模型调用或整个聊天 Session。若任务跨多轮，保留必要的前置上下文和任务内消息；无法确定边界时标记「任务范围待确认」，由审核人选择相关片段，不能把后续纠正内容泄漏到原任务的初始输入中。

缺失、脱敏、截断的内容必须明确标记，不能通过模型补写。只能展示事实，例如「工具退出码为 1，Agent 回答测试通过」，不能直接标为「Runtime 导致错误」。

点击「开始审核」在同一页面展开审核区域；重复点击不重复建单。暂不采用的记录可再次审核，保留历史意见。上传成功不代表允许将其中代码或个人信息直接用于评测集。

### 去重和分类不增加额外页面

- 上传重试：同一 uploadId + 内容摘要幂等接收，不创建第二条记录。
- 内容重复：仅在同一权限范围、同一任务条件下，完整且可比较的上下文、模型/Prompt 版本、工具声明与调用结果、必要初始环境和最终结果一致时，折叠成一组，显示「N 条相同记录」。保留每条来源和时间，可以展开查看；不是删除原始记录。仅任务标题、错误文案或最终回答相同不够。
- 不完整或因脱敏而不可比较的 Trace 不自动合并；语义相似不等于重复，本版不自动做语义去重。
- 分类只用来整理，例如「代码任务」「文本交互」「待分类」。来源声明的类型只是初始值，人工可以调整；同样的分类不代表相同根因，也不参与质量判分。
- 首版一次审核默认整理一个用例，关联同组内各自获准使用的来源。后到的重复记录只追加来源关联，重新检查其授权，不自动重复建用例。一条任务将来可能提炼出多个独立测试，因此不在领域模型中永久锁死「一个 Trace 只能对应一个用例」；幂等针对本次发布操作。

分类只筛选，不自动建议根因。队列按待处理时间提供稳定顺序，故障、反馈或抽样只表示审核来源，不是失败结论。不只保留出错记录，也允许将正常完成和无需触发某行为的记录整理入库，避免用例集只有单侧负例。上传记录经过授权和筛选，其频次不能作为线上故障率。

## 4. 人工审核与用例整理

审核人回答的主要问题是「这条记录能否整理成一个有价值、可独立执行的测试」，不要求先定位根因。

1. 阅读原始任务、回答和工具结果，需要时展开完整记录。
2. 选择「整理为离线用例」「稍后处理」或「暂不采用」；暂不采用需要原因，稍后处理不等于拒绝入库。
3. 在当前页面编辑标题、独立任务输入、明确的验收条件和必要上下文。原始 Trace 与改写内容分开保存；错误的旧回答不预填为标准答案。
4. 文本场景提供独立文本上下文；代码场景选择已审核的独立 fixture（受控的示例项目），或进入“制作环境”子页准备新版本，不能引用用户机器路径。尚未完成环境制作时只能保存用例草稿。
5. 在“发布”节点选择目标集，确认授权用途和隐私检查，点击「检查任务包」。展示逐项检查报告；通过后才启用「发布入库」，由后端重新核验并原子写入审核结果、用例和新数据集版本。未通过保留草稿并提供补充材料入口；材料修改后旧检查失效。原型按钮标注「模拟发布入库」。
6. 保存后可以「审核下一条」，不要求返回列表重新找任务。多人同时审核使用修订号检查冲突，不静默覆盖他人结果。

入库时选择目标评测集，默认「人工审核集」，也可填写名称新建一个。只显示有写入权限且兼容的集合，第三方只读评测集不能写入。版本由后端生成，用户不需要填写数据集 ID、插件 ID 或版本号。隐私确认框只是操作确认，不代替服务端检查、来源授权和人工审查。机器扫描无法保证去除全部隐私，无法确认可复用时不得入库。

期望行为必须可检查。例如场景故意让工具失败，评测检查的是 Agent 是否如实报告失败，不能把这个预设失败的工具退出码直接当成 Agent 评测不通过。

### 用例只要求填四类内容

| 内容       | 用户看到的字段           | 后端保留的语义                                                               |
| ---------- | ------------------------ | ---------------------------------------------------------------------------- |
| 要做什么   | 标题、独立任务输入       | 被测 Agent 真正接收的任务；可以包含执行所需的规则                            |
| 怎样算通过 | 明确的验收条件，逐条填写 | 每项有稳定 ID、是否必选、所需证据和适用验证方式；这些技术信息由模板/后端提供 |
| 在哪里做   | 文本上下文或独立示例项目 | 可重置、可准备的环境及摘要；不带用户机器路径或密钥                           |
| 存到哪里   | 已有集合或新建名称       | 写入权限、来源用途、不可变数据集版本                                         |

可以提供参考答案或正反例，但开放式任务允许不同正确表达，不强制逐字相同。评分器的参考答案和验证实现不能注入被测 Agent；同时，评分要求的行为约束必须能从任务说明中得知，不能用未告知的输出路径或格式要求制造失败。

### 没有合适环境时，进入制作流程

配置资源与网络 → 编辑初始项目 → 准备独立验证器与参考解 → 构建和自检 → 人工复核 → 保存环境版本并回填。Node 合成例子提供可编辑起点；正式版必须由隔离构建 Worker 执行，浏览器不能直接执行脚本或接收主机路径。

自检报告通过六个可点击节点展示材料检查、构建、启动与重置、参考解通过、空跑不通过和重复复现；失败保留日志并停止后续阶段。空跑门槛适用于本修复例子，其他任务需要匹配自身语义的负例。编辑后旧报告失效，重新检查才能发布。

环境版本与数据集版本独立：环境制作成功不自动加入评测集；回填后继续用例验收与入库检查。配方摘要也不等于真实镜像摘要。目录分工与自检环节参考开源任务制作实践，详见 [环境制作设计与依据](eval-environment-authoring.md)。

### 「检查并入库」背后的检查

- 输入自足、必要上下文齐备；待评条件明确且与任务一致，不接受只有「表现优秀」「人格很好」的描述。
- 代码环境能独立准备，验证器不可由被测 Agent 随意改写；新增程序验证有已知正确/错误制品的自检记录，不能空跑全部通过。复用已校验模板时不要求审核人重复配置。
- 文本条件需要人工确认可判断；入库前要求默认 AI 评分器具备针对适用领域的人工校准记录，不能用一次模型自评代替用例审核。新领域或模糊判据先保留草稿。
- 用途、隐私、来源许可、重复用例和目标集合权限通过检查。重复发布幂等；与已有用例完全相同时提示复用，不覆盖其旧版本。
- 基础材料检查默认不调用模型。确需真实试运行时单独告知费用，不能借「入库检查」隐式执行付费任务。

无法复原的线上多轮任务可以人工改写成更小的独立场景，但要标记「局部行为测试」，不能声称覆盖原完整任务。没有可执行环境的历史 Trace 仅留作审核证据，不冒充可执行用例。这是对 [Langfuse 的来源关联与 dataset item 模型](https://langfuse.com/docs/evaluation/experiments/data-model) 加上本项目隐私和独立运行要求后的设计。

## 5. 离线评测

离线评测执行历史是首版 P0 能力，不只是当前运行的临时结果。用户应能找回此前启动的每一次评测，并确认当时跑了什么、执行是否结束、结果和证据是什么。历史查询属于现有「离线评测」入口，不新增顶层导航。

创建实验选择评测集、被测配置与模式。默认重复评测，每题 5 次，可设置 2–20 次；单次冒烟显式设置为 1 次并标注不能判断稳定性。显示“案例数 × 每题次数 = 总试次数”与预算后再确认启动。普通新建使用最新可用集合版本，基线对比使用基线快照；创建时固定版本，不受后续集合变化影响。目录和评分配置来自服务端，不要求用户编写评分规则。默认 5 次是产品起点，不代表统计充分。

目录标记这个集合测什么、是否可运行和默认验证方式。读得懂第三方题目不等于已支持其官方 harness；不支持环境/验证协议时禁用启动并说明原因，不能自动用通用 AI 评分冒充官方成绩。

点击「运行评测」前，后端检查用例、fixture、模型配置、权限与预算，冻结数据集版本、被测 Agent 版本、模型参数和默认评分器版本。涉及真实调用时确认费用；费用包括被测 Agent 和 AI 评审，由平台配置承担，不自动使用上传者的 API Key。

请求创建时持久化任务、冻结快照及全部 Trial 计划并入队后返回，Worker 在后台运行。每条用例的每个试次都先在独立环境执行被测 Agent，再将实际产物与证据交给评分器。成功或失败均继续剩余计划试次，不挑最好一次。默认实现可组合程序检查与 AI 评审，独立于 Agent 执行循环。

每个 Trial 开始于干净的 fixture、会话和可控上下文；不继承上一用例或同题上一试次的 Memory、文件、缓存答案或子 Agent 状态。需要测试记忆的用例显式提供自己的初始记忆。执行参数、模型、Prompt、工具/Skill/MCP 版本、预算和环境摘要由后台冻结，详情可查，不要求启动者逐项填写。

### 离线评测执行历史（P0）

**记录范围与查询**

- 每次成功创建并入队的评测立即形成持久化记录，覆盖排队中、运行中、正在停止、已完成、运行出错、已取消和执行中断；不能只保存成功或最新一次运行。创建失败不伪造历史记录；同一请求重试返回同一记录。
- 默认查询全部离线评测，按创建时间倒序、运行 ID 作为稳定次序，支持分页。可按评测集、执行状态、创建时间范围筛选，按运行 ID 精确查找；筛选属于服务端查询，不只过滤当前页。
- 每条摘要包含运行 ID、评测集名称与冻结版本、被测 Agent / 模型摘要、模式、每题次数、案例数、总试次数、执行状态、创建/开始/结束时间、已处理/总试次数，以及通过、不通过、未判定、未完成数量。尚未开始或结束的时间为空；运行出错不等于全部试次不通过。
- 首次无记录、筛选无匹配、加载中、查询失败分别反馈。查询失败保留已显示数据并标记上次同步时间，重试查询不能触发新的评测。

**历史详情与持久化**

- 按运行 ID 可重新打开同一次评测，读取该次运行的配置快照、逐条结果、判据、异议和执行链路；数据集、模型或评分器的当前配置不能替换历史值。源评测集改名、更新或停用后仍能查看历史快照。
- 刷新、关闭后重新打开、切换入口或服务重启后，记录仍可查询。运行是否继续由后端状态决定；失去 Worker 心跳的任务应按恢复规则标记中断，不因用户查看历史而自动重跑或产生付费调用。
- 新建评测所选的集合与当前查看的历史运行互相独立；详情始终明确标注自身集合和版本。切换集合不篡改历史结果归属，查看旧运行也不停止正在后台执行的任务。
- 历史列表仅返回摘要，样本和事件分页或按需读取；只允许查询当前权限范围的数据，逐层校验运行、样本和事件归属。快照不得包含密钥或真实服务端路径。
- 首版不提供历史删除或自动清理操作。后续按授权撤销或保留策略清理证据时，需明确显示「已清理 / 不可访问」及原因，不能补写证据或把记录呈现为空白成功态；保留范围须服从相应授权与隐私要求。

**重跑与比较边界**

- 首版可通过正常创建流程再次启动评测，每次生成新的运行 ID，旧记录与结果不被覆盖；必须重新检查配置和付费授权。默认创建使用最新可用集合版本，不能声称复现了旧版本。
- P0 支持基于历史冻结配置创建对比实验并关联 baselineJobId，选择已登记的候选被测配置、重新确认费用；必要旧版本不可用时拒绝，不静默替换。只重跑失败子集与用户主动同证据重评分仍为 P1。
- 计划内重复执行各自是独立 Trial；故障重试是同 Trial 下的 ExecutionAttempt，不增加统计分母。重新发起整场评测才是新的历史运行。同证据判卷重试保留 ScoreAttempt，不冒充新的 Agent 执行，也不覆盖原评分。

### 默认评分的规则要透明

优先验证真实产物与状态；例如代码题看独立测试和 diff，工具业务题看预期状态是否发生。语义、沟通和人格要求使用有明确判据的 AI 评审。这个取舍借鉴 [SWE-bench 的执行验证](https://www.swebench.com/SWE-bench/guides/evaluation/) 与 [τ-bench 的结束状态评价](https://arxiv.org/abs/2406.12045)，不是要求所有集合使用同一种算法。

- **通过**：所有必选条件都有足够证据且通过。
- **不通过**：至少一条足以判失败的必选条件被有效证据否定；同时列出其他未完成的检查，不假装已全部检查。
- **未判定**：没有已证实的必选失败，但必要证据缺失、环境/评分故障或不适用，无法得到完整结论。
- 非必选建议、耗时和 Token 默认单列，不冲抵必选失败，也不自动决定质量分。只有任务明确要求的资源约束才参与判定。

工具发生错误后 Agent 成功恢复，不应仅因链路有红色事件就判失败。任务明确要求在预算内完成且证据显示超限，可以判对应条件失败；容器没启动、评审模型超时或日志缺失则是未判定，不能笼统把所有错误算失败，也不能借故障标签排除已证实的任务失败。

默认不要求唯一工具序列。除非授权、安全或任务要求本来就限定过程，否则允许不同有效方案。比如人格中的「简洁」要结合用户要求判断，不能一律奖励短回答、惩罚必要解释。

结果分三层展示，不先铺满技术字段：

1. **总览**：显示案例数、每题次数、已处理/总试次数，以及通过 P、不通过 F、未判定 U、未完成 M；N=P+F+U+M。分别显示计划通过占比 P/N、有效判定成功率 P/(P+F) 及覆盖率 (P+F)/N；分母为 0 显示暂无有效判定，不隐藏 U/M。
2. **案例与试次结果**：每题显示“通过 3/5 次”及全通过、全不通过、结果波动或不完整标签；展开显示所有独立试次，再查看该试次实际输出、判据及证据。不能只展示最好一次或把多个回答合并。每题区间、分类优先级及不完整结果限制见重复评测规格。
3. **详细链路**：点开证据直接定位相关步骤，并可上下查看完整任务。展示实际模型请求及生效 Prompt 来源、当时的工具声明、调用参数与结果、最终回答、独立测试/状态快照，以及评分输入和输出。按实际发生次数展示，不固定为四步；并行工具与子 Agent 按父子关系折叠，不能用一个全局时间排序伪造因果。来源 Trace 单独链接，不代替本次新执行记录，也不展示不可取得的内部推理。

只在总览下加一行次要信息显示耗时与用量，详情区分被测 Agent（含子 Agent）和评分模型。流式用量与累计值不能重复相加，未返回用量显示未知；费用缺少价格依据时不伪造数值，估算注明价格版本。用量是辅助事实，不等于质量。

任务「已完成」不等于全部通过。评分模型超时、评分格式错误、证据不足不能作为质量 0 分；被测输出格式错误是否失败由事先固定的任务要求决定。历史运行保持可选，切换评测集不让旧运行被误认为属于新集合。

默认每题重复 5 次，单次仅为显式冒烟模式。旧单次历史不合并到新实验。比较要求题目、环境、评分、次数与资源策略一致，且有完整有效判定；显示被测配置差异和观测变化，不把换题或放宽评分后的数字当成 Agent 改善，也不自动宣称显著提升或触发晋级。

自动重试只允许确认未调用 Agent 的准备故障最多追加 1 次；Agent 已执行或状态不确定时不自动重跑。判卷格式/传输故障最多追加 1 次，取首个结构有效、引用合法的结果，不因合法不通过而重评；没有有效结论且无已证实必选失败时为未判定。所有尝试和成本保留，均不增加 Trial 数。引用存在不证明 AI 解释正确，仍允许人工质疑。

暂不自动给出根因。需要分析时直接查看实际提示词、回答、工具调用及评分依据；没有收集的内容标记缺失。默认评分器也是可出错的判断，保留版本与依据，便于后续人工核对。

### 人工可以质疑评分，但不需要第三个页面

结果详情提供次级操作「对评分有异议」，填写理由并可附相关步骤，标记为待核对。人工核对记录同意/纠正/仍无法判断，追加作者和理由，不覆盖原机器分。首版总览始终显示机器原始口径，并提示异议数量；人工意见并排展示，不悄悄改变统计。

评分器上线前维护少量人工标注样本，覆盖应通过、不应通过和证据不足；检查误判、漏判及适用范围。日后抽查通过和失败样本，用异议反哺校准。模型自报的 confidence 不当作可靠概率。这一保障基于 [LLM-as-a-Judge 偏差研究](https://arxiv.org/abs/2306.05685)，意见保留历史的方式参考 [Inspect 的评分审计](https://inspect.aisi.org.uk/eval-logs.html)。不在首版另建标注平台。

## 6. 必要状态与异常

- 记录组：待审核 → 整理中 → 已入库；审核中可暂不采用，再次审核保留历史。已接收是传输状态，不要求用户多点一次「提交」。
- 用例：草稿 → 已发布；缺少独立输入、期望或执行环境不得发布。
- 审核暂停仍留队列；入库检查失败保持草稿；结果异议附着到具体评分版本，不改变用例入库状态。
- 运行：排队中 → 运行中 → 已完成 / 运行出错；取消先进入正在停止，确认后已取消；Worker 重启或心跳失效时可进入执行中断。所有状态均纳入执行历史。
- 切换页面保留草稿；生产实现保存到后端，演示只在内存保留，刷新重置。
- 发布使用事务与幂等键，并发编辑检查修订号；重复提交不能生成重复用例。
- 取消运行是协作式取消，已经消耗的调用费用不能撤销；重试保留先前尝试，不覆盖结果。
- Trace 缺失或无权限时明确显示原因，不显示空白成功态；删除/撤销按用途与保留策略联动处理。
- 长文本折行或在代码区域滚动，窄屏顺序阅读；错误靠近操作位置，状态变化不只靠颜色表达。
- 运行结果实时更新不抢走用户焦点，不折叠正在阅读的链路；刷新/返回从后端恢复进度。长列表分页、链路按需加载，后台继续执行不依赖当前页面。

## 7. 架构留扩展点，产品不加操作

数据集通过 DatasetPort 读取统一用例，评分通过 GradingPort 调用默认实现。以后更换数据来源或评分器，只改适配实现与服务端装配，不需要改页面和 Agent Loop；接口和版本记录现在设计清楚即可。

统一返回判据结果、理由、证据引用和原始分值语义，而不是强制所有第三方分数压成同一个 0–100。页面可用约定好的通过/不通过状态展示；不能映射的原始指标只显示原口径，不制造阈值。适配器声明能力，不支持则明确拒绝。

首版不建设通用插件注册平台、评分方案编辑器、自动根因定位、自动优化代码、发布观察流程，也不将用户数据用于训练。未来可在这些接口外增加能力，但不作为本版依赖。

## 8. 首版边界、验收与实施顺序

**P0 必需**：双入口；可用评测集选择与默认配置；计划内重复执行与显式单次冒烟；每 Trial 环境隔离、独立判卷及故障重试边界；带分母和不确定性说明的统计；同条件版本对比；离线评测执行历史、分页筛选与持久化回看；明确必选判据；结果总览、原因与证据下钻；最小人工异议记录；上传幂等、保守去重与人工分类；同页连续审核、草稿、入库检查；授权隔离、取消、并发一致性及费用边界。

**P1 再做**：只重跑失败子集、同证据重评分操作、自适应追加试次、显著性检验及自动发布门禁、辅助相似聚类、一个 Trace 拆多个候选、更多第三方官方 harness、动态用户模拟。不得把重复评测与基本版本对比延后到 P1。

v0.4 HTML 仍是合成数据演示：不上传、不调模型、刷新重置，人工新增用例无真实执行时保持未判定。本轮文字设计新增的交互需要后续同步原型，不能将既有模拟测试算作以下全部能力的验证。

| 验收场景                                       | 必须得到的结果                                               |
| ---------------------------------------------- | ------------------------------------------------------------ |
| 选集启动，之后修改数据集                       | 运行仍使用原快照，展示正确集合和版本                         |
| 连续创建多次评测，刷新或关闭后重新打开         | 每次运行均可按 ID 找回；旧结果不被最新运行覆盖               |
| 存在取消、运行出错和执行中断记录               | 历史均可检索，保留部分结果，未完成不算质量失败               |
| 按集合、状态、时间筛选并跨页查询               | 服务端返回匹配记录，排序稳定；空结果与查询失败有区别         |
| 查看旧运行时切换集合，或源集合更新/停用        | 历史仍显示冻结版本、配置与证据，不误归到新集合               |
| 查询断网、重启恢复、再次启动同一集合           | 查询重试不创建任务；新启动生成新 ID，旧记录不变              |
| 跨任务请求样本证据，或历史证据不可访问         | 拒绝串读；明确缺失或权限状态，不伪造完整结果                 |
| Agent 声称测试通过，独立测试实际失败           | 显示对应必选条件不通过，能点到真实测试证据，不宣称已定位根因 |
| Agent 采用另一条有效工具路径                   | 没有违反任务约束时不能仅因步骤不同判失败                     |
| 工具先失败后恢复；或评测环境没启动             | 前者按最终条件判断，后者未判定并说明故障阶段                 |
| 部分检查失败、部分缺失；取消运行               | 保留全部已知结果与缺失，总数恒等于各状态数量之和             |
| 评分理由引用不存在或无权限的步骤               | 不展示伪证据；评分结果未判定或明确显示内容不可访问           |
| 对一个通过结果提出异议                         | 留下作者、原因、评分版本；原机器结果和统计不被静默覆盖       |
| 相同上传重试、同证据不同来源、仅语义相似       | 分别幂等接收、保留来源后折叠、不自动合并                     |
| 上下文缺失、私有项目路径、含糊判据或验证器空跑 | 不入库为可执行用例，告诉审核人需要补什么                     |
| 多人改稿、重复发布、目标集不可写               | 冲突可见且可恢复；不覆盖、不重复入库                         |
| 页面切换、长链路、并行工具、子 Agent           | 保留草稿/阅读位置；真实关系可查，无虚构顺序                  |

上述验收同时必须通过[重复评测验收清单](eval-repeat-experiments.md#8-验收与实施顺序)。实施顺序：① 实验/Trial/尝试契约、冻结计划与迁移；② 独立环境、重复调度、判卷及统计；③ 历史、证据与同条件比较；④ Trace 审核入库、评分校准与端到端验收。每段按开发 → review 修正 → 测试验收推进；本轮只确定方案，尚不启动业务实现。
